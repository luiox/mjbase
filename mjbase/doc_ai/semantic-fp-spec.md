# 方法语义指纹（semantic_fp）规范

状态：已落地（2026-11-05 状态回填）。按 analysis-db schema v8 method_versions 落地（#154），可达性保守超集等口径与本文一致。原稿 2026-11-02。

## 这个指纹是干什么的

semantic_fp 给每个方法的内容算一个指纹。方法体没变，指纹不变；方法体变了，指纹必变。

它有两个用处：

1. 省算力：方法体没变，旧的分析结果直接复用，不重算。
2. 精确失效：方法体变了，只重算受影响的方法，不整库重来。

核心不变量一句话：语义变了指纹必须变，语义没变指纹必须不变。指纹该变不变，会拿旧结果配新代码，算错；不该变变了，增量就失去意义。本文所有规则都是这句话的展开。

## 指纹怎么算

三步：收集语义面，归一化，哈希。

### 第一步：收集方法的语义面

- 方法头：描述符、访问标志、异常表。方法名不进指纹——方法叫什么由身份层管，内容指纹只管内容。
- 指令流：只取从入口可达的指令，按原 pc 升序排列。这个遍历序就是规范序：删死代码后的保序压缩，不是任何重排后的布局序。异常处理器入口一律按可达根处理（保守超集：守卫区死了处理器也算可达），宁可多算可达、不漏。每条指令记 opcode 和操作数。
- 异常表：每条处理器记录覆盖范围、处理入口、捕获类型。
- Code 属性里的 max_stack 和 max_locals。

不进指纹的东西：行号表、局部变量表、SourceFile、注解、参数名、StackMapTable（它是方法体的派生物，方法体不变它不该自己变）。要看渲染效果的缓存另有 render_fp，不混用。

### 第二步：把每条指令归一化

原则一句话：分析看得见的差别才算差别。逐族定案：

| 指令操作数 | 记成什么 | 为什么 |
|---|---|---|
| 常量加载（iconst/bipush/sipush/ldc int） | 「int 值」一个 token | iconst_5 和 ldc 5 分析看得见的结果一样，常量折叠不改指纹 |
| ldc 字符串 | modified-UTF-8 原始字节 | 不做字符集解释 |
| 类型（NEW/CHECKCAST/INSTANCEOF 等） | 解析后的类名 | 不记常量池编号 |
| 字段/方法引用 | （类，名字，描述符）三元组 | 不记常量池编号 |
| invokedynamic | 名字、描述符、bootstrap 方法句柄、全部静态参数 | 与 indy 解析面同一约定 |
| 分支目标 | 规范序里的指令序号 | pc 会漂移，序号不会 |
| 局部槽位 | 原样 | def-use 分析对槽位分配敏感，不重编号 |

常量加载是 v1 唯一做跨编码归一的地方。别扩大：比如 goto 和反向条件分支互换不改，因为那是控制流图变化，必须翻指纹。

### 第三步：序列化并哈希

- 序列化：类型化 token 流，变长整数、定长字段小端、字符串带字节长度前缀。流的开头放一个算法版本号（v1 = 0x01）。
- 哈希：SHA-256，取 32 字节，文本形态 64 位小写 hex。
- 确定性：同一份字节，任何机器任何时间算出来必须一样。序列化里不许出现指针值、哈希表遍历序、平台相关的整数类型。CI 覆盖 Windows 和 Linux 双端一致。

### 算法版本

归一化规则以后要改（加等价族、换遍历序），版本号必须加一。旧指纹靠版本位自然作废，不用迁移，GC 收走。

## 什么改动会翻指纹

这张表是测试矩阵，也是使用方的预期。新增等价规则，先改这张表再写代码。

| 改动 | 指纹 | 原因 |
|---|---|---|
| 常量折叠（ldc 换 iconst） | 不变 | 常量等价族 |
| 删死代码、插死代码 | 不变 | 只看可达指令 |
| 打乱指令布局、加对齐填充 | 不变 | 只看规范序 |
| 重排常量池、重写索引 | 不变 | 全部解引用 |
| 改行号、LVT、注解 | 不变 | 排除面 |
| 改 opcode（iadd 换 isub） | 变 | 语义变了 |
| 增删异常处理器 | 变 | 异常表参与 |
| 改访问标志 | 变 | 方法头参与 |
| 改 indy bootstrap 参数 | 变 | 解引用面 |
| 被引用的类/方法改名 | 变 | 见下 |

改名要单独说：指纹里包含被引用的名字，这是有意的。分析事实的出口语义就是名字，被引用的类改名了，旧事实的指向已经不对，指纹就该翻。注意 rename 引擎的显示名覆盖不改字节码，不触发这个问题；真正的字节码批量改名会大面积翻指纹，这是正确成本，不做豁免。

规范序与「布局不变」的边界（PoC 收口定案）：规范序定义为存活指令按原 pc 升序的保序压缩，「打乱指令布局不变」只覆盖不改变存活指令相对顺序的变化（偏移漂移、对齐填充、死代码增删）。真正的存活块重排翻指纹——这是保守选择的已知代价：指纹为增量复用服务，多翻只损失复用，漏翻会拿旧结果配新代码。要召回块重排等价属算法升级，走版本号加一，不在 v1 做。

## 怎么接进数据库

- 每个方法版本落一份指纹（method_versions）；编辑方法体时在同一个事务里做四件事：算新指纹、存新版本、更新当前指针、标脏。
- local_facts 的主键里有指纹，指纹一翻自然查不中旧事实，旧事实留着等 GC。
- 边表按源方法替换时带上当前指纹（analysis-database.md §4.3 的写事务约定）。
- native 和 abstract 方法没有方法体：指纹只盖方法头，永远恒定。

## PoC 实测（2026-11-03，混淆语料 261 类 / 1629 方法）

按本规范实现的原型全量过验收三条：1629 方法双算（重新解包重解析）逐方法一致；向每类常量池注入 18 个垃圾条目逼出全量重索引后 1629 个指纹零变化；整 jar 重打包重读再算同样零变化。唯一性：1629 方法得 1521 个指纹，21 个多重组共 129 个方法全部为真实同体（组内规范化 token 流逐字节一致），不同语义零碰撞。期望表 10 行全过，表外补验 3 条：方法自身改名不进指纹（21845 字节空格名真实样本实测不变）；被引用空格名字段改名翻引用者指纹；native/abstract 只盖方法头。语料覆盖 indy 1501 条、switch 283 条、wide 158 条。

待评审定案的剩余边界 8 项，原型各自选定了一种口径。下表的原型口径为 PoC 实现事实，不是规范定案，逐项过目后才进 v1。

| 边界项 | 原型口径 | 备注 |
|---|---|---|
| 异常表 pc 到存活序号的映射口径 | 覆盖范围端点映射为「pc 不小于端点的首条存活指令」的规范序号，end 不含，越过末尾取存活总数 | handler 必须精确落在存活指令上，否则报错拒绝；catchType 解引用为类名，0 记空；表项顺序原样保留 |
| 方法头是否含所属类名与 Exceptions 属性 | 不含：方法头只写算法版本、原始访问标志 u16、方法描述符 | 所属类名、方法名、Exceptions、Signature、注解、MethodParameters 全程不读不记 |
| 非 int 常量折叠边界（FCONST_1 与 ldc float 是否同指） | 不同指：跨编码折叠只限 int 族，iconst、bipush、sipush、ldc Integer 归一为「int 值」token | lconst、fconst、dconst 记 plain opcode 原字节；ldc 的 float、double、long 记原始位型，不做 NaN 规范化 |
| ldc 的 Class/MethodType/MethodHandle/condy 载荷解引用深度 | 全部解到语义值：Class 解为类名，MethodType 解为描述符串，MethodHandle 解为（kind，类，名字，描述符），condy 按 indy 同款记名字、描述符、BSM 句柄、全部静态参数 | ldc、ldc_w、ldc2_w 的 opcode 本身不进流，同载荷同 token |
| 访问标志是否剔除编译器旗标 | 不剔除：记原始 u16 | BRIDGE、SYNTHETIC、VARARGS 等编译器旗标原样参与指纹 |
| wide 前缀是否并入 opcode | 不并入：wide 前缀不进指纹，指令按 base opcode 归一记 | wide 与非 wide 同语义同 token，槽位与增量照常记实际值 |
| bootstrap 方法参数解引用深度 | 解一整层：BSM 句柄解到（kind，类，名字，描述符），静态参数逐个按类型解引用 | 参数里的 Class、MethodType、MethodHandle 都展开到语义值；参数位再嵌 condy 或 indy 直接报错，不递归 |
| switch key 表是否原样进指纹 | 原样进指纹：tableswitch 按 low 加序号重推出连续 key 全列，lookupswitch 逐 case 记原始 key 值 | 每个 key 配目标的规范序号，default 目标先记，顺序与 class 文件一致 |

## 实现与验收

- 承载在 mjbase 分析层，输入 jbc DOM，不新写第二套解析。
- 验收三条：常量池重排 + 布局重排 + 死代码删除三连之后指纹不变；任何真实语义编辑之后指纹必变；Windows 和 Linux 算出的指纹一致。

## 明确不做

- 不跨方法：被调方只记身份三元组。被调方内容变了怎么办，由摘要的 deps_hash 机制管，不在本规范里。
- 不追语义保持混淆：插无害指令序列这类对抗手段会翻指纹。指纹为增量分析服务，不为对抗服务。
- 不做版本迁移：算法升级不重算旧指纹，旧档靠 GC 退场。
