# 已知库识别（library identification）

状态：部分落地（2026-11-05 状态回填）。L1 前缀分类已落地（census origin 列，library_origin jdk/known/unknown）；shape_fp 与 L2 形状匹配未落地，待批。原稿 2026-11-02。

## 要解决的问题

拿到一个混淆过的 jar，现在没法回答「哪些类其实是 gson、kotlin-stdlib、JDK」。分不出来有三个代价：census 基线的数字被库代码污染；rename 连库符号一起改，映射文件全是噪音；分析查询被 JDK 内部调用淹没。

识别的目的只有一个：把容器分成「业务代码」和「库代码」两本账。识别结果只用来分层、标注、过滤——不改写任何字节，映射文件里永远不出现库符号。

JVM 域是这件事的便宜域：官方前缀白送、描述符白送类型系统、常量池白送证据面。

## 三层做法

从便宜到贵，三层各自独立可用，前面挡不住的漏给后面。

### 第一层：包前缀（零成本）

java/、javax/、jdk/、sun/ 这些官方前缀一眼可分；gson、org/json 这类第三方坐标前缀建一张表。实现是编译期常量表加一个分类投影，不动 schema。census 导出加一列 origin，取值 jdk / known / unknown。

这条的边界要诚实：前缀可以被混淆器抹掉。但抹 JDK 前缀需要重链接，风险大收益小，多数混淆器不动它。所以第一层只敢说「确定是库」，不敢说「带未知前缀就不是库」。

### 第二层：残留证据

前缀被抹了，库还会漏马脚。三类信号，全部来自已经入库的数据，不用重扫容器：

1. META-INF/maven 段、manifest 的 Class-Path、pom.properties 版本串。实测混淆产物大多保留——手头样本 jar 里的 gson 残留就是活例子。
2. 版本字符串、license 头这类特征字面量。字符串加密会杀掉这条信号，失效就落到第三层。
3. 结构形态：成员数量、描述符分布、超类链指向。单独不算证据，给第三层当预筛。

### 第三层：形状指纹匹配（核心）

难点一句话：库被改名后，库内部自己的引用也跟着改名了，拿原版库的指纹直接比对必然失配——semantic_fp 里包含被引用的名字。

解法：指纹做两个味道。

- semantic_fp：名字原样参与，给增量分析用（见 semantic-fp-spec.md）。
- shape_fp：名字抽象掉。被引用的类只记「容器内还是容器外」，成员名记占位符，描述符原样保留，描述符里的类型名按同样规则递归。指令流和类型骨架全保留。

为什么这样就行：改名混淆只改名字字面量，不改指令流，不改描述符结构。所以 shape_fp(改名后的库方法) == shape_fp(原版库方法)，对绝大多数方法成立。

匹配流程：

1. 参考库 jar 按普通流程摄入分析库，inputs 表的 role 列写 reference。这个列已经在 schema 里，不用动表。
2. 参考语料按「类形状哈希」（成员描述符多重集加访问标志）建倒排索引。
3. 容器里的 unknown 类查索引，拿到候选。
4. 候选类和目标类按描述符对齐方法，逐方法比 shape_fp，多重集算 Jaccard 相似度。超过阈值、方法数够多，才算匹配。方法数门槛必须有——太小的类结构撞车概率高。
5. 匹配结果写 local_facts，config_hash 里带语料坐标和版本，事实键机制免费复用。报告单独出 TSV，展示层做标注。

置信度：相似度阈值、规模门槛、语料版本一起给结论。两个库形状撞车就并列报告，不强行仲裁，交人工。kotlin 这类跨编译器版本形状会漂移的库，语料按版本锁死，不做跨版本容差。

## 实施顺序

1. 第一层前缀分类 + census origin 列。无依赖，随时可以开工。
2. 第二层残留证据。无依赖。
3. shape_fp 和匹配。依赖 semantic-fp-spec 的规范化 token 流先落地——token 流做好了，加一个名字抽象开关就是 shape_fp。

## 明确不做

- 不做语义等价证明。形状匹配是统计证据，不是证明。
- 不做语料自动采集。参考库由人按坐标入库，语料治理是数据工作不是代码工作。
- 不做识别结果的自动改写。识别只分层、标注、过滤。
