# 已知库识别（library identification）

分析数据库设计没有「参考库/签名包」概念（审查确认的唯一盲区）：面对一个
混淆容器，现状无法回答「哪些类其实是 gson / kotlin-stdlib / JDK」。
本文给出分层识别设计。JVM 域是 FLIRT 的便宜域：官方前缀白送、描述符白送
类型系统、常量池白送静态证据面。

## 定位

识别的目的不是逆向库本身，而是把容器**分层**：

- census 基线分出「业务代码」与「库代码」两本账，量化口径不再被库噪音
  污染；
- rename 引擎拿到免改名清单（库符号不进映射文件，映射 diff 干净）；
- 分析查询可按来源过滤（调用图、xref 不再被 JDK 内部边淹没）；
- 识别结论作为显示层标注（库里同名类标回原始坐标），不参与任何改写。

## 分层

三层从廉价到昂贵，逐层兜底，每层独立可用。

### L1 包前缀分类

零成本确定性层。参考输入是官方前缀集合（`java/`、`javax/`、`jdk/`、
`sun/`、`com/sun/` 及内部前缀）加常见第三方坐标前缀表（
`com/google/gson`、`org/json` 等）。

- 承载形态：编译期常量表 + 分类投影，不动 schema。census 导出加
  `origin` 列（`jdk` / `known` / `unknown`），分类规则版本随导出表头
  版本走。
- 诚实边界：前缀是混淆器最容易保真的部分（改写 JDK 引用需要重链接，
  风险收益不成比例），但业务类被扔进伪装前缀、库被去掉前缀都存在。
  L1 只回答「确定是库」和「确定不是证据」，不回答反向。

### L2 结构与常量证据

前缀被抹掉后的证据层。三类信号，全部来自已入库事实，不重扫容器：

1. **残留元数据**：`META-INF/maven` 段、manifest `Class-Path`、
   `pom.properties` 版本串——实测混淆产物普遍保留（现有样本 jar 的
   gson 残留即此形态）。
2. **字符串证据**：版本字符串、license 头、库特征字面量。字符串加密
   会杀死这条信号，失效即落入 L3。
3. **结构形态**：成员数量与描述符多重集哈希、超类链指向已知前缀、
   注解与异常类型面。单独不成证据，作 L3 候选预筛。

### L3 形状指纹匹配（改名后库识别）

核心问题：库被字节码级改名后，**自身引用也一起被改名**——包含被引用
名字的 `semantic_fp` 必然失配，直接比对原版库指纹无效。

解法是指纹的双味道化：规范化 token 流参数化一个「名字可见性」开关。

- `semantic_fp`（名字满味）：被引用名字原样参与——为增量分析服务，
  见 semantic-fp-spec.md。
- `shape_fp`（形状味）：同一 token 流，被引用名字抽象化——owner 降为
  「同容器内/外部」二元标记，成员名降为占位符，**描述符原样保留**
  （描述符里的类型名递归同规则）。方法的形状指纹 = 自己的 opcode 流 +
  全部类型/描述符骨架，不含任何名字。

库被改名只改名字面，不改描述符结构与指令流（混淆器不重排指令语义），
故 `shape_fp(改名库方法) == shape_fp(原版库方法)` 对绝大多数方法成立。

匹配算法：

1. **语料入库**：参考库 jar（maven 坐标 + 版本登记进 `inputs`，
   `role = reference` 列已存在，不动 schema）按普通流程摄入分析库。
2. **类级预筛**：参考语料按类形状哈希（成员描述符多重集 + 访问标志面）
   建倒排；目标容器 unknown 类查倒排得候选集。
3. **方法级验证**：候选类与目标类按描述符对齐方法集，`shape_fp`
   多重集求 Jaccard 相似度，超阈值且规模达下限（方法数门槛，小类
   结构碰撞概率不可接受）即判匹配。
4. **输出**：匹配写入 `local_facts`（producer = 库识别，`config_hash`
   覆盖语料坐标与版本），事实键机制免费复用；报告独立 TSV，展示层
   标注走 renames 旁路注释，不写映射。

置信度与歧义：相似度阈值 + 规模门槛 + 语料版本三元组进结论；同形状
不同库的碰撞按多候选并报不强行仲裁，交人工。跨编译器版本（如
kotlin 各版 stdlib）形状会漂移，语料按库版本锁死，不做跨版本容差。

## 与设施的接线

- 全部判定走 producer 层：分类 producer（L1）与匹配 producer（L2/L3）
  的事实都进 `local_facts`，键里的 `config_hash` 天然隔离语料版本。
- census 导出：v1 加 `origin` 列；L3 匹配报告独立成表，不挤 class
  census 的列契约（schema 版本不受此影响）。
- 查询面：AnalysisDb 加按 origin 过滤的查询投影（薄投影原则，
  分类结果是事实不是存储）。

## 边界（明确不做）

- 不做字节码语义等价证明；shape_fp 匹配是统计证据不是证明。
- 不做运行时反射构造的库形态识别。
- 不做语料自动采集与版本嗅探：参考库由人按坐标入库，语料治理是
  数据工作不是代码工作。
- 不把识别结果直接用于改写：识别只分层、标注、过滤，映射文件永远
  不含库符号。

## 实施顺序

1. L1 前缀分类 + census origin 列（独立可交付，无依赖）。
2. L2 常量证据（独立可交付）。
3. shape_fp（依赖 semantic-fp-spec 的规范化 token 流先行落地，
   加开关即可）+ 匹配 producer + 报告 TSV。
