# 迁移切片与公私边界

本仓（mjbase）是公开仓。改动前先读这份文件：它规定**什么能进本仓**、
**按什么顺序进**，以及**迁移与重构如何不打架**。

## 一、公私边界（红线，不可协商）

mjt-deobf 及其混淆器家族设施**不能开源**。本仓一旦混入这些内容，等于
把私有资产和私有坐标系（混淆器厂商、版本特解的对抗面）公开出去。

| 内容 | 归属 |
|---|---|
| 通用能力：keys / 容器 / 映射 / 指令工程 / 引用索引 / pass 契约 / AIR-SIR | **本仓（公开）** |
| renamer（重命名引擎，通用能力，非家族专属） | **本仓（公开）** |
| 混淆器家族特解：各商业混淆器的探测、解密、扁平化还原 | **不进本仓** |
| 同一家族的多版本策略（各版本算法差异） | **不进本仓** |
| keep 预设库里对标商业混淆器默认排除表的模式数据 | **不进本仓** |

执行口径：

- **家族名不出现在公开仓**——源码、注释、测试用例、issue 引用都不写。
  公开的是"能解"的机制，不是"解谁、怎么解"。
- **通用能力只在本仓出现一次**。家族设施里不许重写通用分析（那正是
  老式 deobf 工具膨胀的复辟路径）。
- 家族设施以**插件 + 数据供给**形态挂在私有侧的 deobf 宿主上：
  keep 规则引擎（DSL/glob/档位）公开，模式表由私有侧喂入。

## 二、为什么按切片迁移，而不是整库搬运

整库搬运 = 一次性继承全部未审问题（编码口径、生命周期约定、依赖环），
且没有消费方约束时，无法判断哪些面真正需要。切片的原则是**消费方驱动**：
mjt-mcp 与 mjt-py 实际 include 什么，就迁什么。

## 三、迁移与重构的解耦（顺序纪律）

两者撞车是因为都盯同一批文件。它们其实作用于不同层次：

- **迁移**决定文件在哪个仓（物理位置）
- **重构**决定模块间的依赖方向（逻辑结构）

因此**不做"先全局重构再迁移"，也不做"先全量迁移再重构"**，而是逐批交替：

```
落一批切片 → 该切片内部破环 / 拆 target → 验证全绿 → 下一批
```

每批的重构只碰本批内部，不跨批改。这样任何一个时刻，仓里都是"已验证的
一批 + 未迁的剩余"，不存在半成品的全局状态。

### 批次与各自要处理的环

依赖普查（`mjbase/<mod>/...` 全限定 include）实测的环：

1. `asm ⇄ analysis ⇄ reference`（asm 越层 include reference / spi）
2. `pass ⇄ spi`（pass→spi 26 处、spi→pass 14 处，最大的环）
3. `air / sir → spi` 反向边（IR 层不该知道 pass 契约层）

| 批次 | 模块 | 落仓时要处理的环 |
|---|---|---|
| 1（已落） | keys / util / expr / jar / mapping / model / project / consumer | 无（零内依赖叶子） |
| 2（已落） | asm 域 + hierarchy | 环 1 的 asm 侧 |
| 3（已落） | reference + analysis + spi + pass | 环 1 余下 + 环 2（主战场）；reference_scan 先落直写切片，class-string 反射事实已随 mjt-mcp 契约补齐，反射事实族其余（成员查找/handle/lambda bootstrap/别名）待主线落 |
| 4（已落） | renamer + workspace | 无新增；workspace 的 remap/rename/pipeline/workflow 方法族随 mjt-mcp 消费面补齐 |
| 5（部分落） | jasm / cli / log 已落；air / sir 未落 | 环 3 |

include 全走 `mjbase/<mod>/...` 全限定形式，所以**分 target 不需要改动任何
include**，边界由构建图强制——这正是本仓此前缺失的 gate。

## 四、每批的验收

1. **构建门**：`rm <exe> && xmake -r <target>` 后运行，内容哈希增量会骗人
2. 全绿（跳过项须注明原因，如 POSIX-only）
3. **依赖图检查**：本批模块不得 include 未落仓的模块（跨批依赖即为切片切错）
4. 公私边界复查：本批不得出现家族名与混淆器专名
